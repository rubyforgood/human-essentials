Option A — the filter goes inside the card, under the tab striprecommended

The tab strip becomes a fixed landmark: same position on every tab, whatever is below it. A tab that filters shows its filters in its own panel; a tab that does not, does not. Only the table moves, which is the tab's content and is supposed to change.

Groups — the strip has not moved

  • design.md already says this. "Nothing sits between a tab strip and the first row of its table except that table's own filters." These pages put the filter above the strip instead, which is how the strip ended up moving.
  • The filter belongs to the tab, so it lives in the tab. Reading order finally matches ownership: you are on Partners, and these are the Partners filters.
  • It already has to submit into a frame, which it does — so the strip is not re-rendered by filtering.

Option B — give every tab a filter bar so they matchrejected

The symmetrical answer: add a search box to Groups and to Item categories so all tabs look alike.

It invents a control to fill a hole. Groups has 2 rows and Item categories has 3 — measured. A filter over three rows is furniture, and every reader pays a row of chrome for it on every visit. If either list grows enough to need filtering it should get one on its own merits, and Option A means adding it then costs nothing and moves nothing.

Option C — reserve the filter's height when a tab has nonerejected

Keep the filter where it is, and give the tabs without one a 54px spacer.

A blank 54px band that means nothing, on a page whose whole job is to show a list. It fixes the jump by paying its cost permanently, and it still leaves the filter sitting above a strip it does not belong to.

What the industry does

SystemWhere per-view controls sit
GitHubRepo tabs are fixed chrome; each tab's own toolbar — the Issues filter bar, the Actions search — sits below the strip and differs per tab.
Jira, Linear, NotionTab or view switcher pinned; filters and sort belong to the view, rendered under it.
Ant Design, Material, CarbonEverything that varies goes in the tab panel. The tablist is chrome.
SalesforceList view selector fixed; the list's own controls below it.

None of them makes every tab carry the same controls, and none of them reserves empty space. The invariant they all keep is that the strip does not move — a tab is a place, and a place that shifts when you arrive is the thing that reads as broken.

And the sidebaralready fixed

Reported in the same breath: "when the user clicks on groups, it automatically collapses the side nav." It did, and so did Inventory when you opened Item categories. The rail decides which section to keep open from the current controller, and its list named only partners and items — so on partner_groups and item_categories nothing was active, and the whole section shut underneath the reader.

Industry standard is not in doubt here: GitHub, GitLab, Jira and Linear all keep the section open and the parent entry marked while you are anywhere inside it. That is a bug rather than a design choice, so it is already fixed — measured before: /partner_groups and /item_categories had no open group at all; after: Network and Inventory stay open with their entry marked.

Recommendation

Option A. It is what design.md already asks for, what every system above does, and the only one that fixes the jump without either inventing a control or reserving a hole. Groups and Item categories keep no filter, because two rows and three rows do not need one — and when one of them does, it can be added without moving anything.
