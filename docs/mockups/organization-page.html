The organization page kept its old body

Reported as looking unmigrated. The shell was migrated — page header, card, no Bootstrap classes anywhere — and then the 28 fields inside it were left as they were. That is why it passes every automated check and still looks wrong.

“the organization view page is an issue, it looks like it was not migrated at all. The one you get to from the organization button on the bottom left or from the avatar dropdown”
What is wrongMeasured on the live page
Fields are flat <p> stacks28 label/value pairs, zero <dl> — every other detail page in the app uses a <dl> grid
Dividers are nearly black6 <hr> at oklch(0.208 0.042 265.755) — slate-900. An unstyled <hr> inherits currentColor under preflight; the app's dividers are slate-200
No vertical rhythm7 different gaps between fields: 24, 36, 44, 45, 54, 61, 93px
Title Case labels15 of 28 — "Default intake Storage Location", "Enable Partners to make child-based Requests?"

Invalid nesting2 empty <p> the browser manufactured; </address> is closed inside an if branch and there is a stray </p>

The invalid nesting is the one to note: it is the same class of defect as the three profile partials that closed wrappers they never opened, and it is invisible to every check the app has — the page returns 200, carries no legacy class, and throws no JavaScript error.

A — one card, bands, and a two-column list

Recommended

Keep it as one card. Each of the eight sections becomes a band — the same tinted strip the line item card uses to separate a change of kind — and the fields inside it become a <dl> on a two-column grid, which is what every other detail page in this app already does. One gap number throughout, no icons, sentence case.

Two columns rather than four because the labels in the approval and request sections are long enough that four would wrap every one of them.

Correction, measured after building it: this does not shorten the page, which is what this preview originally predicted. The card went 1,519px to 1,516px — the eight band strips cost about 368px, which is almost exactly what two columns save. The case for A is consistency and the broken markup, not height.

C — repair only

Leaves the layout

Fix the broken nesting, recolour the six rules to the hairline, regularise the gaps to one number and put the labels in sentence case — and leave the one-column <p> stack alone. It is the smallest change and it fixes everything that is broken, but the page still would not look like the rest of the app, which is what was reported.

What I would ship

A. It is the layout the app already uses for a record's details, it halves the page's height, and it fixes the broken markup on the way through. B is defensible but turns one record into eight cards; C leaves the reported problem in place.

Whichever you pick, the same three go with it: the six near-black rules become the design system's hairline, the 15 Title Case labels become sentence case, and the per-row icons go — design.md already argues that case for repeated rows.
