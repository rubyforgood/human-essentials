Manufacturer donations, redesigned

Six things are wrong with this page and four of them are the same thing: it is the one report that is not a table.

1. What is there now

Recent manufacturer donations

Manufacturer 1 (2,901)
The list is a <div class="manufacturer"> per row, and that class is defined nowhere. So the link renders in near-black with no underline — it does not look like a link, and it is the only way into the manufacturer.
FaultDetail
Not a tableThe other five reports are tables. This is a list of bare divs: no column headings, no alignment, no totals, nothing to scan down.
(2,901) has no unitIt is sum(line_items.quantity) — items, not donations — but the model calls the column donation_count and the page prints it bare. The stat directly above says Items donated 2,901, the same number, so the page shows one figure twice and labels it once.
A date the page has and never showsThe query already selects max(donations.issued_at) as donation_date and orders by it. The reader is shown a list in date order with no dates in it.
Capped at 10, silentlyby_donation_date(10, …). A bank with more manufacturers is shown ten and not told.
“1 Manufacturer”pluralize(1, "Manufacturer"), under a label already reading Manufacturers donating — the word twice, and a capital M mid-value against sentence case.
A page action in the card bodyNew donation sits between the list and the footer. Page actions go in the page header.

  • For: identical to the app's other five reports, so it inherits their row height, their numeric alignment, their scroll region and their sparkline column if it ever wants one. The figures become scannable and the date stops being invisible.

A ranked table with an in-row bar is the standard shape for “top N by a measure” — it is what GA4's report tables and Stripe's breakdowns do. The bar is redundant to the figure beside it, which is the point: it is there to be scanned, not read.
  • For: relative size at a glance without a chart, and no series-count problem — a bar per row scales to any number of rows, unlike a series per manufacturer.
  • Against: a bar is a graphical object and needs a text alternative; the percentage beside it is that. Sorting largest-first also loses the “most recent” order the query was built for, so one of the two has to give.

4. Option C — a chart above the table

Named for completeness and not recommended. The number of manufacturers is set by the data, not by the design — the rule this app arrived at after the 47-series trend chart and the unbounded category stack. A bar per row inside the table, as in B, gets the same reading without a series count.

Rejected on the rule already written down, rather than on taste.
Recommendation: A, with B's share bar. Make it a table first — that fixes four of the six faults at once, because the missing unit, the missing date, the missing total and the unscannable layout are all consequences of not having columns. Then add the share bar and the rank, because “which manufacturers matter most” is the question this report exists to answer, and a bar per row answers it without a chart.

The other two faults are copy and placement: the count gets a unit (“6 manufacturers”, sentence case, not repeating its own label), the ten-row cap gets said out loud in the subtitle, and New donation moves to the page header where every other page action lives.

Which order should the table be in? The query orders by most recent donation and B sorts largest first. I would keep largest first and put the date in its column — the page is a summary of who gives most, and “recent” is already the date range's job. Tell me if you would rather it stayed chronological.
