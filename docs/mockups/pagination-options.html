Pagination

Measured against the running app. Nothing here is built — the question at the end is which page-size rule you want.

1One defect, and it is the worst page in the app

items_controller.rb:23 computes pagination and throws it away. It assigns @paginated_items, and that name appears nowhere else in the repository — not a view, not a spec. The view renders @items, all 51 of them, at 121px a row: a 6,442px page with no pagination control. Dead code hiding a missing feature.

/admin/base_items is the same shape without the dead code: 47 rows, 2,867px, unpaginated, and global to every organisation.

2Which tables should paginate at all

Not a row count. The question is whether a collection is bounded by the size of the organisation or grows with its activity. A list of three storage locations does not want a pager; a list of donations does, from the first day, because the page that is fine at 20 rows is unusable at 2,000 and nobody notices the day it crosses over.

Grows withTablesRule
Activity adjustments audits barcode_items broadcast_announcements distributions donations events product_drives purchases requests transfers Always paginate
The organisation donation_sites items kits manufacturers partner_groups partners product_drive_participants storage_locations users vendors Filter instead — except items, below

Three of the first group are unpaginated today — audits, barcode_items and broadcast_announcements — plus transfers, which is filed as bounded but is not: a bank transfers stock between locations forever.

items is the exception in the second group. It is bounded, but at 121px a row a bank with 200 items gets a 24,000px page, and 51 items already gives 6,442px. Height decides it, not the category.

3How many rows — the measurement that changes the answer

The usual answer is 25 or 50: Kaminari defaults to 25, GitHub uses 30, Shopify, Jira, Linear and Salesforce use 50, Stripe 20, Django admin 100. The split in that list is row height — 50 where rows are one line, 25 where they are tall.

This app does not have one row height. It has sixteen, and they differ by 4.5× — 45px on /users, 205px on /purchases. A single page size cannot serve both.

4The development page size hides all of this

config.default_per_page is 5 in development and staging, and 50 in production. Nobody building or reviewing this app ever sees the layout that ships: a table that is eleven screens in production is one screen in staging.

That is a review gap, and it is the kind that lets a 6,442px page through. Whatever page size you choose, it should be the same everywhere.

5The control itself does not change

6What I would build

1. Fix items: render @paginated_items and add the pagination partial. Two lines, and it takes the worst page in the app from 6,442px to 1,815px.

2. Paginate the four that grow and do not: audits, barcode_items, broadcast_announcements, transfers — plus admin/base_items.

3. Adopt B, the three bands, as a per-controller constant, and make the development and staging size match production so the layout under review is the layout that ships.

4. Write the bounded/unbounded rule into design.md, so nobody paginates a list of three storage locations.

A or B — and do you want the four extra tables paginated now?
