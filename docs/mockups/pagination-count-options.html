The count on single-page tables

Two questions in one: should a table that fits on one page still say how many rows it has, and should the control set stay put instead of appearing and disappearing? Measured in this app on 20 August 2026.

What happens today

Two separate reflows, and the second one is not the one you asked about but is the same problem:

  • One page → no strip at all. The card simply ends after the last row, so nothing says how many rows matched. Nine of the sixteen index pages are in this state on the seed data.
  • The pager itself reflows as you page. « First and ‹ Prev are not rendered at all on page 1, and Next and Last are not rendered on the last page. On /requests that is 7 controls on page 1, 14 on page 5 and 8 on page 10 — the row of buttons changes width under the cursor every time you use it.
  • The screen-reader announcement gives up. When a filter applies, auto_submit_controller announces the new count — except on a paginated page, where it says “Results updated”, because the rows on screen are not the total and it has nothing else to read. Any option below fixes that as a side effect.

Option A — the strip is always there, and so are the controls

Recommended

The footer renders whatever the row count, and a control that leads nowhere is drawn disabled rather than removed. This is the majority convention in dense admin tables: Stripe, Shopify Polaris (whose docs say pagination should stay visible for consistency), Material UI TablePagination, Ant Design (which ships hideOnSinglePage: false by default) and AG Grid.

  • For: the card has the same shape whatever the data, and the buttons stop moving under the cursor. Every table says how many rows matched, which is the question the filter bar raises.
  • For, on accessibility: disabled here means a <span aria-disabled="true">, not a disabled link. That is already this app's rule — ui_helper.rb renders an unavailable action as a non-focusable span for exactly this reason, because a disabled link stays focusable and announces nothing.
  • Against: four dead controls under a three-row table is visible chrome that does nothing. Stripe and Material show only a disabled Prev/Next pair, not First and Last as well.

Option B — the count is always there, the controls only when they lead somewhere

The strip always renders and always states the total; the buttons appear only when there is a second page. This is Django admin, which prints “9 items” under every list and adds page links only when it needs them.

3 requests

  • For: no dead chrome. The sentence shortens honestly — “3 requests” rather than “Showing 1–3 of 3 requests”, which states a range nobody needed.
  • Against: it answers the count question but not the reflow one. The pager still grows and shrinks between pages unless that is fixed separately, and the strip still changes height class between a one-page and a multi-page table.

Option C — the count belongs to the table, not to the pager

The count moves into the card header, where it is part of the table's identity and is there whether or not there is a pager. The footer appears only when there is more than one page. This is GitHub (the count is in the Open/Closed tabs above the list), Salesforce Lightning (“20 items • sorted by Name” in the list header) and Linear.

  • For: the count sits with the thing it counts and reads before the table rather than after it, which is the order you want when the question is “did that filter do anything?”
  • Against: most index cards in this app have no header at all — they are padded: false with the table meeting the card edge. This would add a 57px header to sixteen pages, directly under a summary card that already carries a scope sentence saying much the same thing. Two counts, 60px apart.

Recommendation

Option A, with Stripe's control set rather than the full one. Keep the strip always, keep the controls always, but the persistent pair is ‹ Prev and Next › — disabled when they lead nowhere — with « First and Last » appearing only on a table that has more than one page.

That gets the whole benefit — a card of stable shape, a count on every table, and buttons that stop moving between pages — without putting four dead controls under a three-row table. First and Last are worth keeping when they mean something, because jumping to the oldest record is a real task on audits and events; under a one-page table they mean nothing at all.

Not C, only because of where this app puts things: sixteen index cards would grow a header they do not currently have, immediately below a summary card that already states the scope. If those cards had titles, C would be the better idea.

Whichever is chosen

Having the total in the DOM on every table lets the filter announcement stop hedging. auto_submit_controller.summary() currently returns the literal string “Results updated” on any page with a pager, because the rows on screen are not the total and announcing the page size as if it were the count would be worse than saying nothing. With a count always present it can read the real sentence instead, on every page.
