Pagination designs

Four ways to render the pager, all built from components this design system already has. Every number below was measured in this app on 20 August 2026, not estimated.

What exists today

Already built

Yes — the system has a pagination component: shared/essentials/_pagination, five Kaminari templates in app/views/kaminari/, and a .pagination-link class in the stylesheet. It is a numbered pager on a hairline strip at the foot of the table card, with aria-current="page" on the current number. It is in use on fourteen pages.

The gap: “Page 3 of 19” never says how many rows there are. A user looking at /requests cannot tell from this whether the filter matched 140 records or 1,400, and page count is a proxy that changes meaning whenever the page size does.

Option A — keep the numbered pager, add the count

Recommended

One change: the label states the range and the total instead of the page number. Same markup, same component, same keyboard behaviour. This is what Stripe, Shopify Admin, GitHub’s issue lists and Django admin all put on the left of the pager.

  • For: answers “how big is this result set?”, which is the question the filter bar above it raises. Keeps direct access to the last page — the one people use to find the oldest record.
  • Against: the row of numbers is the widest control on the strip; at 19 pages it needs the ellipsis to stay on one line.
  • Cost: one helper, one partial. No change to any call site.

Option B — range summary with prev/next only

Drop the numbers entirely. Two ghost buttons and a count. This is Linear, Notion, Vercel and the newer Stripe dashboards — the pattern that admits nobody types a page number, they scan and step.

  • For: narrowest control on the strip; survives a phone viewport without wrapping; no ellipsis logic.
  • Against: reaching page 19 of /requests is eighteen clicks. There is no way to jump to the end, and this app has tables where the oldest record is the interesting one (audits, events).
  • Cost: a new partial; the five Kaminari templates stop being used.

Option C — range summary, prev/next, and a page-size control

Option B plus a “rows per page” select. This is what Material, Ant Design and AG Grid ship as the default, and what most enterprise admin tables do.

  • For: the user resolves the row-height problem themselves; a power user on a tall monitor picks 100 and stops paging.
  • Against: it makes a per-user preference out of a decision the design just made. The banded sizes exist precisely because 50 is wrong for /purchases and 15 is wrong for /users; a select invites the wrong answer and then has to remember it per table, per user. It also adds a fourth control to a strip that already competes with the filter bar for attention.
  • Cost: a control, a permitted param, per-table persistence, and a decision about where the preference lives.

Option D — load more / infinite scroll

No pager. A button appends the next page into the same table.

  • For: no page state to keep in the URL; reads well on a phone.
  • Against: wrong for this app. These are working tables, not feeds — you print a distribution, you Ctrl-F an item, you send someone a link to what you are looking at. A loaded-in row cannot be linked to, the browser’s find only sees what has been appended, and the footer of the page moves away from the user every time they reach it.
  • Cost: a Stimulus controller, a Turbo Stream append action per table, and every system spec that counts rows has to learn to wait.

Recommendation

Option A. It is the smallest change that fixes the one thing wrong with the pager we have — that it never says how many rows matched — and it keeps the last-page jump, which the audit and event tables genuinely need.

Not C: a rows-per-page select hands the user a decision the banded sizes were introduced to settle, and it has to be remembered per table and per user to be worth anything. Not D: these tables get printed, searched and linked to.

B is a reasonable second choice if the numbered row ever becomes a problem on narrow viewports — but at the banded sizes the longest pager in the app is /requests at nineteen pages, which fits on one line with an ellipsis.
