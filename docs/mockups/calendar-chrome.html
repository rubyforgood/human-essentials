The calendar is wearing FullCalendar's clothes

And the design system already says what to do about that. The font is not actually different — the calendar renders in Figtree, same as everything else. What reads as a different typeface is 16px at weight 400 against the app's 14px at 500.

Three filled dark buttons is the loudest part. The app allows a page one primary, and this page's real action — "Copy calendar URL" — is a quiet secondary sitting above three navy blocks that are only there to move the month.

The design system already answers this

design.md: "select2 is restyled, not vendored as-is. It ships a 28px-tall, 4px-radius, 16px-text control in a #aaa border, and the app's is 38px, 8px and 14px in slate-300… beside a plain input all six read as a control from a different application."

Those are the same numbers. 4px radius, 16px text, a grey outside the palette. FullCalendar and select2 are the same vintage and ship the same defaults; select2 got the treatment and the calendar never did.

There is a second precedent pointing the other way, and it is worth naming: Litepicker was deleted rather than restyled, because native <input type="date"> does that job. That is the test — is there a native control for this? For a month grid of events there is not, so this is the select2 case, not the Litepicker case.

What to do about it

A — Restyle it, exactly as select2 was recommended

Unlayered rules in application.css mapping FullCalendar's chrome onto the app's tokens: the buttons become :secondary at the 38px control height, prev/next become icon buttons, the title becomes a card title, the grid takes slate-200, and events become brand chips.

  • For: it is the convention the app already has for a vendored widget, with the same numbers. Nothing new to decide.
  • For: no behaviour changes, so no new specs for month navigation, event loading or the iCal feed.
  • For: FullCalendar's classes are stable and documented, and the app already overrides two of them.
  • Against: a CSS contract with a dependency. If FullCalendar 7 renames a class the styling silently reverts — which is exactly what already happened here, since nobody restyled it when select2 was done.

B — Replace it with a month grid of our own

A table of days, built from the same components as everything else.

  • For: matches by construction rather than by re-theming — the argument that removed Litepicker.
  • For: drops four jspm pins.
  • Against: FullCalendar is doing real work here — event layout within a day, overflow when a day is full, the list view on mobile, timezone handling through Luxon. That is a lot to rebuild for a page most banks open occasionally.
  • Against: the Litepicker argument does not transfer. There it was native input versus dependency; here there is no native month grid.

C — Replace the toolbar only, keep the grid

Turn off FullCalendar's header (headerToolbar: false) and render Today, prev, next and the month title as ordinary app components that call calendar.today(), .prev(), .next().

  • For: the buttons stop being a CSS contract and become real components — they cannot silently revert on a library upgrade.
  • For: it fixes the loudest part, the three navy buttons, with the least CSS.
  • Against: the grid still needs the token pass from A, so this is A plus extra work rather than an alternative to it.
  • Against: more JavaScript to own, and the button state (is "prev" available?) becomes ours to track.

Recommendation

A, with the toolbar part of C.

Restyle the grid in CSS, because that is what the app already does for a vendored widget and the numbers are literally the same. But take the toolbar out of FullCalendar's hands entirely, because that is where the damage is most visible and where a CSS contract is least worth having — three buttons are cheap to own, and they stop being able to revert.

Not B. The Litepicker precedent is about replacing a dependency with a native control, and there is no native month grid. Rebuilding event layout, day overflow, the mobile list view and timezone handling is a great deal of work to make a page look right that a token pass fixes.

And the subtitle

"Scheduled distributions, by day." is the subtitle rule failing in its own words: it defines the page's title back at you. It also undersells what the page is for — the one action on it is Copy calendar URL, which subscribes a real calendar application to this feed.
