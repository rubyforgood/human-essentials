Filters and batch actions at the same time

Reported: "the print pick lists batch action makes the filter disappear... They should not be mutually exclusive." That is correct, and the reasoning I recorded for it does not survive checking.

What I got wrongmy error

design.md currently says the bar replaces the filter row because "three of the four keep it in the toolbar" and "covering the filters while a selection is live is the right behaviour... Carbon answers it the same way". Both claims are weaker than I made them:

SystemOn selectionAre the filters still reachable?
Carbon (IBM)The batch bar covers the table toolbarNo — the one system that does this
GitHubThe list header becomes batch actionsYes — the filter bar above it is untouched
GmailThe action toolbar gains archive, delete, labelsYes — search is a separate bar and stays
Linear, Notion, Airtable, DriveA floating bar near the bottomYes — nothing above is covered

I generalised from Carbon. Gmail's toolbar is its action toolbar, not its search; GitHub's batch header replaces a list header that sits below the filters. Only Carbon actually takes the filters away, and I cited the other three as agreeing with it.

And the layout argument contradicted my own rule. I wrote that "an inserted row moves the table and a replaced one does not" — but bin/design/layout-shift-audit.js, written the day before, skips shifts the reader caused: "opening a disclosure or applying a filter is supposed to move what is below it". Ticking a checkbox is exactly that. Chrome excludes it from CLS for the same reason.

Option A — the bar sits under the filtersalternative

Both present, in the flow, nothing covered. This is GitHub's shape: persistent filters, and a row below them that becomes the batch actions. Tick a row.

  • Cost: the table moves down about 70px when you tick. That is a shift you caused, which is the kind this app already accepts everywhere — the filter panel does the same when it opens.
  • Risk: the bar is pinned to the top of the list. This page is 1,289px against a 900px viewport, so if you scroll down to tick a row near the bottom, the bar — and the action — is off screen.

Option B — the bar floats over the listrecommended

Nothing is covered, nothing moves, and the actions stay with you as you scroll. This is Linear, Notion, Airtable and Google Drive, and the reason all four use it is exactly the risk above: selecting happens while scrolling. Tick a few, then scroll the list.

  • The filters never move and are never covered. Neither is the totals button.
  • Nothing in the page shifts — the bar is over the content, not in it.
  • It follows you down the list, which is the whole point: on a 15-row page you are usually scrolled when you finish choosing.
  • Cost: it covers a sliver of the last row while it is up, and it is a dark surface the app does not otherwise have. It only exists while something is selected, which is the argument for letting it be distinct.

Recommendation

Option B. It is the only one that keeps the filters, the totals button and the batch action all reachable at once and stays reachable itself when you have scrolled to the bottom of the list to make the selection. A is a fair second and simpler to build; the reason to prefer B is the 1,289px page, not fashion.
