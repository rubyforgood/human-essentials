What the design system says today, and why you are still right

The written convention is that tables scroll. “A table row is one line… a sideways scroll is a deliberate act you take once. WCAG 1.4.10 Reflow exempts data tables from the no-sideways-scroll rule for this reason.” It cites Carbon, Material, Stripe and Linear, all of which do scroll.

But the Reflow exemption is permission, not advice — it says a data table is allowed to scroll, not that 80% of one should be off screen.

And the system already contradicts itself. The line item row in a donation stacks below sm, drops its heading row, and gives every cell its own label — and the reason recorded for it was that “four columns at 320px leaves the item picker 72px, which is not a control anyone can use.” Nine columns of purchase data at 286px is the same argument. So the pattern is already in the system; it just was not applied to the tables.

Three ways to stack it

Every panel is resizable — drag the bottom-right corner to take it below 44rem, then below 26rem.

A — Every field, labelled

All nine columns become labelled fields: one column of them when the space is very narrow, two when there is room. Nothing is hidden and nothing is decided for the reader.

  • Against: tall. Nine fields × fourteen rows is 126 labelled values on one page.
  • Against: a label for every value repeats the heading fourteen times, which is exactly what a table exists to avoid.

B — The first few fields, and the rest behind a disclosure recommended

The identifying field and the three that answer “which one is this and what happened” stay; the rest fold away per row. This is what Shopify Polaris, Filament and most mobile admin UIs do: a record summary, expandable.

C — Every field, with the action on the title line

Option A, except the row's action sits beside the record's name rather than at the foot of the card — so the card reads like a list item with a control, which is the more usual shape.

Two things any of these needs

1. The labels have to come from somewhere, and it should not be 299 hand-written attributes.

Every demo above uses data-label on the cell, which the CSS reads with attr(). Writing those by hand means touching 299 headings across 71 views and keeping them in step forever. A controller can copy them out of <thead> by column index instead — one place, always in step, and it works for a table that arrives in a Turbo frame. Without JavaScript the table simply stays a scrolling table, which is what it is today.

2. Changing display on a table removes its semantics.

A browser stops exposing rows and cells as a table once display is not table. The fix is explicit ARIA — role="table", role="row", role="cell" — added by the same controller, so the tree says the same thing at both layouts. This is the part most implementations of this pattern get wrong, and it is invisible unless you look at the accessibility tree rather than the page.

Recommendation

B, with the container query and the controller-supplied labels and roles.

A and C are honest and simple, and they produce a very long page: nine fields on fourteen records is 126 labelled values, and a label repeated fourteen times is the thing a table exists to avoid. B keeps the list scannable, which is the point of an index page — you are there to find one record, not to read them all.

The cost of B is fifteen judgements about which fields lead, and I would rather make those explicitly than pretend all nine matter equally at 320px. For /purchases: who it was from, what it cost, when, and where it went.

If you would rather not have fifteen arguments, A is the safe answer and needs no per-table decisions at all — say so and I will build that instead.
