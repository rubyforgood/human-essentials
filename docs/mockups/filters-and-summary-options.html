1Why the inputs are different sizes

The bar is flex flex-wrap items-end gap-3 and each control sits in a min-w-[13rem] box. A flex item sizes to its content — the longest option in the menu — so the widths come out ragged, and flex-wrap packs each line to the left and leaves whatever is left over. Measured on the real pages:

2Filtering as you choose, instead of a Filter button

You are right that it is the standard, and right that the button is an extra click. The split in practice is by how many filters and how expensive the update is: Linear, GitHub, Notion and Stripe apply each control immediately; Jira's advanced search, the AWS console and Salesforce report builder keep an Apply button because the query is costly and people set several conditions before they mean anything.

This app already does both — five pages auto-apply, eleven have the button — which is the actual inconsistency.

The thing that decides this is not the button. application.js line 12 sets Turbo.session.drive = false, so a filter submit is a full page reload: the whole document, the sidebar, the assets, scroll position back to the top, and focus back to the start of the page.

Auto-applying nine filters that way means up to nine full reloads while someone is still deciding, each one throwing away where they were. That is why the button is there on the busy pages, and it is a real reason rather than an oversight.

So there are two ways to give you auto-filtering, and they are very different sizes of job:

OptionWhat happensCost
A — auto-submit everywhere Set auto_submit: true on the remaining eleven bars. Selects apply on change; the date range applies when a preset is picked, and waits for both dates when Custom is open; text filters debounce. Full page reload per change. Scroll and focus lost each time. Roughly two hours.
B — wrap the results in a Turbo Frame first, then auto-submit The table, the summary card and the pagination update in place. No reload, scroll and focus kept, and a change costs one small request instead of a whole document. The right answer, and the bigger one: a frame per index page, plus data-turbo-frame on the form. Turbo Drive stays off, so nothing else on the page changes behaviour.

Either way the Filter button goes. Both need a live region announcing the new result count, because a filter that applies silently tells a screen reader nothing, and a busy indicator so a slow query does not look like nothing happened.

I would do B, and I would do it as its own change rather than folded into a layout fix. If you want the quick win now, A on the pages with three filters or fewer is safe and I can do it in the same pass as the grid.

3“Default (recent and upcoming)”

Fair — it does not say what it covers. It is two months back to one month ahead. The window runs into the future on purpose, because a distribution can be scheduled before it happens, and a range ending today would hide everything already booked in.

LabelReading
Default (recent and upcoming)Current. “Default” says nothing, and the parenthetical is vague.
Last 2 months and next monthSays exactly what it is, in the same shape as “Last 30 days”. My recommendation.
Recent and scheduledBetter than “upcoming”, still does not give the span.
Around today (2 months back, 1 month ahead)Precise and too long for a menu.

Separate question worth asking once: should the default still be this window at all, or plain Last 30 days like most reporting tools? Changing it changes what every index page shows on first load, and would hide scheduled distributions, so I would rename and leave the behaviour alone unless you want that.

4A subheader for the summary card

The card has no title, so the period caption above it is doing two jobs and reads as though it might belong to the table. What is actually unclear is scope: that these figures describe the filtered view rather than everything.

5What I would build

1. The grid filter bar, on all sixteen bars. Fixes the ragged widths and the trailing white space, and is independent of everything else here.

2. Rename the preset to Last 2 months and next month. Behaviour unchanged.

3. Summary card option B: header “Totals”, subheader naming the count, the filter state and the period.

4. Auto-filtering as option B — a Turbo Frame around the results, then auto-submit and drop the button — as its own change, because doing it by full page reload would make the busy pages worse, not better.
