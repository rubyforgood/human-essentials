Reaching a row's actions in a wide table

Reported: "having the action all the way at the end of a horizontal scroll for a user who is processing multiple rows is a very frustrating experience." Every table below scrolls — drag them sideways to feel the difference. Numbers are measured from the running app.

And it does not stay scrolled. Acting on a row reloads the page, and a reload puts scrollLeft back to 0 — measured: 402 → 0. So processing a page of 15 distributions at 1440 is 402px × 15 = 6,030px of horizontal dragging, re-done from scratch after every single action. That is the frustration, and it is not a feeling — it is arithmetic.

One group is unaffected: keyboard users. Measured — one Tab from the row's first link jumps straight to "More actions" and the browser scrolls it into view for free. The person paying for this layout is specifically the one using a mouse.

Option A — pin the actions column to the right edgerecommended

The actions column stops scrolling and stays against the right edge, exactly as the first column already stays against the left. The reader keeps both anchors: what the row is, and what they can do with it. A shadow appears on its left while there is still content hidden behind it, and goes when there is not. Scroll this one.

  • Zero scrolling to act, at every viewport. 818px becomes 0px on the worst table.
  • It survives the reload. The actions never move, so resetting scrollLeft costs nothing.

  • It composes with everything else here — you can pin the column and still add selection later.
  • Cost: the pinned column covers ~90px of the table while you scroll. It is the narrowest column, and the shadow says something is behind it.

Option C — select rows, act on them togethercomplement, not a replacement

The direct answer to processing multiple rows: tick several, act once. This is Carbon's TableBatchActions, and the pattern in Gmail, GitHub, Linear, Airtable and Jira. Tick a box.

What pinning costs a table with visible buttonsmeasured

Nothing at all, unless the table scrolls. position: sticky is inert in a container that does not overflow, so the widest actions columns in the app — /manufacturers at 428px, /barcode_items 321px, /item_categories 284px — cost nothing, because none of those three scroll. Those numbers are the table stretching its last column to fill the row, not the buttons needing the room. The separator and shadow will only be drawn while something is actually hidden behind the column, so on a table that fits, nothing changes visually either.

Should they all collapse into the menu? No — design.md already settles this, and collapsing a settled pair would hide a one-click action behind two clicks on every row, forever, to save width that only costs anything at some viewports. The existing rule is: three or more on any row, or a set that varies by status, role or state, gets the menu; a settled one or two stays visible.

Checked against that rule, exactly one of the six is wrong today: /kits branches on kit.active to show Deactivate or Reactivate, which is the varying-set case, and it is also the widest at 273px. That is a bug against a rule already written, not a new decision.

The better lever is one design.md already contains. It says a visible action beside a kebab is icon-only at 28px, named by aria-label and title. Extending that to any inline actions column takes every labelled pair to a uniform 94px — measured, by stripping the labels in the live page — which is narrower than three of the five kebab columns, and costs no extra click at all.

Nobody moves actions to the left (Option B). Pinning the action column to the right is the settled answer, and the systems that also offer batch selection offer it in addition, never instead.

Recommendation

Option A now — it removes up to 818px of scrolling per action, survives the reload that currently throws the reader back to the left, costs nothing to learn, and is symmetric with the pinned first column already in the app. Option C next, on the tables where a batch action genuinely exists; it composes with A rather than competing. Option D is the real fix for /distributions' twelve columns, but it needs a column chooser and a stored preference, so it is its own piece of work rather than part of this one.
