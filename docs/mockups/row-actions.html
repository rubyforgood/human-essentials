Row actions: one treatment for every table

Measured across 31 tables in two roles on the running app. design.md already settles most of this — every row action is :ghost, three or more collapse into a menu, the trigger is size-7. The problem is that the rule is applied per row rather than per table, and it says nothing about a column whose action set changes from row to row. Both gaps are visible below.

Option A — collapse by table, not by row recommended

Two amendments to the rule that already exists, and nothing else changes:

  • The threshold is per table. If any row in a table can reach three actions, every row in that table gets the menu. Tables with a fixed set of one or two keep them inline.
  • A varying action set is itself a reason to collapse. If which actions exist depends on status, role or state, use the menu — the trigger is the same 28px on every row whatever is inside it, so the column stops moving.
  • An unavailable action stays in the menu, disabled, with the reason as sr-only text. design.md already says this; it only ever applied to tables that had a menu.
  • A visible action beside a kebab matches its height — both 28px.

Option B — a kebab on every table, always most uniform

Total consistency: the actions column is one 28px control on every row of every table in the app, with no exceptions to remember. The cost is real and design.md already names it — every action becomes two clicks, and "a warehouse user printing picklists all afternoon will feel Print moving behind a menu". Tables like /kits and /manufacturers have a settled pair of actions that work fine inline today.

Option C — one visible action plus a kebab, everywhere alternative

Every table shows exactly one visible control — the row's most common action — with the rest behind a kebab. The column is a stable 96px everywhere and the common case stays one click. The difficulty is that "the most common action" is a judgement per table, and on /partners there is no single answer: the row that wants Review profile and the row that wants Request recertification are different rows.

Recommendation: A. It is the rule design.md already has, with the threshold moved from the row to the table and one sentence added about a varying action set — which is exactly the case that produced the complaint. It fixes all three measured problems, changes 10 tables rather than 22, and keeps one click on the tables where the actions are settled and the column is already stable. B is defensible if uniformity matters more than the click, and is the smaller rule to hold in your head. C reads well but needs someone to nominate a primary action for 26 tables, and /partners shows that is not always answerable.
