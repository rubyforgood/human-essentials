Two follow-ups on table actions

The actions column header, and why a disabled action gives no reason. Both measured on the running app after the row-actions change.

1. The actions column header

Industry practice is genuinely split, and it splits along what the column contains. Salesforce Lightning uses assistive text; GOV.UK uses govuk-visually-hidden; Carbon and Atlassian render the header empty with an accessible name. Ant Design — the most table-heavy of them — shows a visible Action column. The W3C tables tutorial only requires that every column have a header, visible or not.

A correction to what I said last time. I justified hiding it partly on width — "a visible label widens a 60px column". Measured, it costs 15px on /partners and /items and 18px on /donation_sites. That is not a real cost and I should not have leaned on it.

Why I now recommend B, having recommended A a commit ago: the facts changed. When the column held labelled buttons — Edit, Delete — it described itself and a header was redundant. Collapsing nine tables turned most of these columns into a single unlabelled glyph. A column whose entire visible content is "⋯" is exactly the case where the header is doing work, and 15px is a fair price for naming it. Hidden headers suit columns of labelled controls; this is no longer that.

2. Why is Deactivate greyed out? confusing today

Reported on Items, and it is a real defect I introduced. The reason exists — it is just invisible to the person looking at it. It is sr-only text, so a screen reader reads "Deactivate, unavailable while this item is still in inventory or used by a kit" and a sighted user sees a grey word and nothing else. There is no tooltip either.

What it looks like now

✎Edit
⊘Deactivate…

Greyed, no explanation, no hover target. why?

A — the reason, visible recommended

✎Edit
⊘DeactivateStill in inventory or used by a kit

Readable by everyone, no hover, no click. answers it

The alternatives, and why not

OptionWhat happensVerdict
A. Visible help text under the label The reason is a second line in the menu item, always on screen. This is Polaris's helpText on an ActionList item. Recommended. No hover, no touch problem, one place for the sentence, and the screen-reader text it already has becomes the visible text.
B. Tooltip on hover The reason appears when you point at the item. No. A disabled control fires no pointer events, so the tooltip needs a wrapper element to work at all — and there is no hover on a phone.
C. Do not disable; explain on click GOV.UK's position: no disabled controls. Clicking shows why it cannot be done. Honest, and it spends a click and a page load to deliver one sentence that would fit on the row.
D. Omit the action entirely What this did before the row-actions change. No. It is what made the column ragged, and "the button is missing" answers nothing.

The wording changes too. "— unavailable while this item is still in inventory or used by a kit" was written to be read after the label by a screen reader, which is why it starts with a dash. As visible text it becomes its own sentence: "Still in inventory or used by a kit". Every reason gets the same treatment — a storage location that still holds stock, a partner group that still has partners.
