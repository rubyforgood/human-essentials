The row menu: three things

One was a plain bug and is already fixed. Two are open questions.

1. Why the menu looked wrong fixed

Not a spacing choice — a layout bug, and you were right that it made no sense. An enabled action was rendered through the button helper, which applies inline-flex justify-center and wraps the form in inline-block. The actions cell is text-right, and an inline-block inherits that — so the item shrank to its own width and floated to the right edge, inside a menu sized by everything else.

Measured on /vendors: Edit at x=1 across the full 222px; Deactivate at x=117, 106px wide. Every enabled action in every row menu was like that. It is a plain button_to with the menu item's own classes now — all items x=1, 222px wide, glyphs at x=13, across all nine menus.

A, still — but B is a fair choice and here is the honest trade. A tells you before you spend the click; B has room to say what to do about it, which one line under a label does not. GOV.UK's position is that a disabled control is never the answer because the user cannot tell "not allowed" from "broken". This app is a back-office tool where users repeat the same task, so learning "greyed out means still in stock" once is cheap — that is the case for A. If you would rather never grey anything out, B is coherent and I would take the banner text further than the line above.

How it missed every audit — three reasons, all of them real

AuditWhy it could not see this
overlay-audit.js It finds triggers with [data-action*='dialog#open'] and opens <dialog> elements. A native confirm is not in the DOM at all — it is browser chrome. There is no element to query, so the audit that exists precisely to open dialogs cannot open this one.
wcag-audit.js / axe axe scans the document. Same reason: nothing to scan.
The system suite It depends on it. These specs use Capybara's accept_confirm, which drives a native dialog. So a green suite is evidence for the browser dialog, not against it — the same shape as the toastr message and the frozen-column shadow earlier on this branch: the assertion pins the thing that is wrong.

The check that would have caught it is not a DOM query — it is asking Playwright whether a dialog event fires when a destructive control is clicked. That is a handful of lines and it is the missing audit.

Scope, honestly: 44 call sites, and every accept_confirm in the suite has to become a click on a real button. It is the largest of the three changes here and worth doing on its own rather than folded into this one.
