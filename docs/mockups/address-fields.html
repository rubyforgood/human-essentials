Address fields: one box, or four?

Reported on the vendor form. Everything on this page below the first section is already built and pushed — the shared definition, the autocomplete tokens, the ZIP fix, the audit. The one thing left to decide is whether the four freeform addresses become four fields.

Where the app stands now

Option A — leave the four as one box what happens if you do nothing

New vendor

autocomplete="street-address"

  • Nothing to migrate. No schema change, no backfill, the four CSV import templates keep working.
  • Still inconsistent with the other three screens, which is what was reported.
  • You cannot filter or group by state, because there is no state. This is why donation sites cannot be listed by region.
  • Geocoding keeps working exactly as it does today.
Does not answer the report.

Option B — four fields, and the CSV keeps one column recommended

New vendor

  • The same four fields as the organization form, from the same address_field definition, so all seven screens match.
  • The CSV templates do not change. The importer keeps a single address column and parses it; a bank's saved template file still works.
  • The old column stays as a composed #address method, exactly as Organization does it — so geocoding, the four PDFs and the exports need no changes at all.
  • State becomes filterable on donation sites, vendors and storage locations.
Cost: a migration on 4 tables, a backfill, and an importer that parses.

The backfill is the risk, and it is measurable

Splitting existing text is where this can lose data. Measured against the seed database — 10 of 18 rows parse cleanly:

DonationSite882345 NE Some St., Pawnee, IN 12345

Seed data is not production data, so those proportions are indicative only. The safe handling is the same either way: put whatever does not parse into Street address unchanged and leave city, state and ZIP blank, so nothing is ever thrown away and a human can finish the ones the parser could not. Nothing is deleted by the migration.

Option C — four fields, and the CSV gains columns rejected

The same form as B, but the import templates become name,street,city,state,zipcode,…. Cleaner on paper, and rejected: 200+ banks have downloaded these templates and keep local copies, and a bank whose saved file still has one address column would get a silent import failure at the point it is least able to debug one. B gets the same result without breaking a file somebody already has.
