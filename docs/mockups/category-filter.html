The category filter, at three and at fifty

Before building A+B, what the category control should be. I measured what this app already does with long lists first, because the answer changes the recommendation.

The app's existing answer to “one of many” is a plain native select, at any length. Eight pages already put 52 items in one, and a time zone picker holds 153. That is a real precedent, and it cuts both ways: matching it is consistent, and improving only the category filter makes one control special while 54 others stay as they are.

2. What is published

Verified this morning rather than recalled — I fetched each of these:

  • GOV.UK maintains accessible-autocomplete as a separate component, whose stated purpose is “helping users choose answers from a list you provide” and whose first design goal is accessibility. A design system shipping a whole separate component for choosing from a list is itself the signal about what a long <select> costs.
  • IBM Carbon ships ComboBox and Shopify Polaris ships Combobox, both distinct from their plain Select.
  • I could not fetch GOV.UK's prose guidance on when to avoid a select — it lives on their website, not in the repository — so I am not quoting it.

3. Option A — leave it a plain select

Native. No JavaScript, works with every screen reader and every mobile picker, and identical to the other 142.
  • For: consistent with the whole app; nothing to get wrong; a phone renders it as its own full-screen wheel, which is genuinely good at 50.
  • Against: on a desktop, 50 options is a long scroll with no way to jump except typing the first letter.

4. Option B — a searchable popover recommended

The shape this page already uses twice: a trigger showing the current choice, and a panel with a list. The date range picker and the month range picker are both this, so it adds no new vocabulary — the only new part is a filter box above the list.

Category

Why this one. It is the same control the reader has already used for the months, one field to the left. It scales to any number of categories without a threshold, and it avoids the full combobox ARIA surface — the panel is a dialog with a text field and a list of buttons, exactly like the month picker that is already built and has specs.

Search appears where it earns its place; the list is the same at 3 or 300.
  • For: one pattern, already in the design system and already tested here; scales without a cliff; the search box is the only new part.
  • Against: heavier than a select for a bank with three categories, and it is a custom control — keyboard support has to be written and kept working, where a native select gets it free.

5. Option C — a real combobox

Category
Type to narrow. What Carbon, Polaris and GOV.UK's autocomplete all ship — and the largest ARIA surface of the three: role="combobox", managed aria-activedescendant, announced result counts, and behaviour that differs between screen readers.

6. Option D — no category filter at all

If the table drives the chart, the table is where you pick things — a Category column you can sort and filter in place, and no separate control above it. Worth naming because it is the cheapest answer, and because it removes a control rather than improving one.

  • For: nothing to design; the long list problem does not arise.
  • Against: the filter narrows the chart as well as the table, which a column cannot do; and it makes “show me only period products” a two-step job.
Recommendation: B, the searchable popover — but with a caveat I want to state rather than bury. It is right on its own terms: one pattern, already built here, scales without a threshold. The caveat is that it makes this the only searchable list in an app with 54 selects over 50 options, including 52-item pickers on eight pages that matter more than this filter does. If B is worth building here it is worth extracting for those too, and I would rather that be a decision than an accident.

If you would rather not open that door: take A. A plain select is defensible, consistent, and native — and the honest reason to choose it is that the app's long-list problem is bigger than this filter and should be solved once, deliberately, not sideways through a report page.

Either way I would add the count to the label — Category (15) — so the length is visible before the control is opened.
