The fade says there is more. Nothing lets you go and get it.

Three separate defects, all measured on the running app at 1440×900. The first is a mistake in what shipped; the other two are the reason a fade on its own was never enough.

1. The fade covers the pinned column — you are right, and it is wrong

When you scroll right, the shipped CSS draws a 40px white gradient at left: 0. That is exactly where the pinned column sits. So it dims a column that is not moving, and it obscures the one column pinning exists to keep readable.

WCAG 1.4.3 wants 4.5:1 for normal text. And that is the darkest pixel of the glyph; a column-by-column profile shows 19 of the 26 inked columns lifted, the worst from 63 to 164.

axe reported no violations on all 156 pages. It computes contrast from declared colours, so it cannot see a gradient painted on top by a pseudo-element. One more audit checking a proxy rather than the thing.

Six of the seven tables that overflow have a sticky pinned column. Only /items does not.

2. What triggers the scrollbar: a gesture you have already started

It is an overlay scrollbar. It reserves 0px of height — measured on all twelve regions — and the platform paints it only while a scroll is in progress, then fades it out. So it can never tell you that scrolling is possible; it can only confirm it once you have guessed.

And the styling I shipped to fix that cannot work as written. Chrome ignores ::-webkit-scrollbar entirely on any element that also sets the standard scrollbar-width or scrollbar-color — and .table-scroll sets both.

I could not prove that here either way: no combination of --disable-features=OverlayScrollbar, FluentOverlayScrollbar,FluentScrollbar makes headless Chromium 141 reserve a single pixel, with or without the pseudo-element. Which is the argument for not depending on it: a control that renders differently on every platform cannot be the answer to “I don't see it”.

3. The control is below the fold

Your third point, and the one that decides this. Even a perfectly visible scrollbar sits at the bottom of the table — and the table is taller than the window.

The correction, which belongs in every option

No left fade. The pinned column casts a shadow to its right instead, and it deepens only once content has actually passed underneath. This is what Carbon, Ant Design, AG Grid and Airtable all do: the shadow marks the boundary between what is frozen and what is moving.

Four ways to make the columns reachable

A — The corrected fade, and nothing else

Fix the pinned column, leave the rest. Shift+wheel, a trackpad swipe, the arrow keys once the region has focus.

  • For: nothing new to learn, no chrome, no JavaScript beyond what is there.
  • Against: it does not answer your complaint. It tells you there is more and leaves you to work out how — and a mouse user with a wheel and no horizontal tilt has one option, which is to scroll the whole page down to find the scrollbar.

B — A scroll control that rides the fold recommended

A slim track pinned to the bottom of the viewport for as long as any part of the table is on screen, so the control is always within reach of the rows you are reading. Drawn from two divs rather than left to the platform, because that is the only way it looks the same everywhere.

Where this is used: Ant Design ships it as a first-class table prop (<Table sticky />); Confluence and Jira both float a horizontal scrollbar on wide tables; DataTables has had a plugin for it for a decade. It exists precisely for a table that sits in page flow and is taller than the window — which is every table here.

Drag the thumb, click the track, or focus it and use the arrow keys. In the app the strip is sticky; bottom: 0 so it follows you up the page; here it sits where it lands at the table's end.

  • For: answers all three complaints at once. Visible at rest, on every platform, without scrolling to the bottom. It is a real target you can drag, and it needs no gesture knowledge.
  • For: it is a genuine control, so it can carry role="scrollbar" and the arrow keys — the fade cannot be operated by anyone.
  • Against: it is a scrollbar we draw, so it is ours to maintain: drag, click-to-page, touch, and the ARIA. Roughly 80 lines of Stimulus.
  • Against: one more horizontal band on the page. Cheap at 20px, but not free.
  • Against: a sticky element at the bottom of the viewport has to yield to anything else that lives there. Nothing does today.

C — Bound the table's height, spreadsheet style

Give the region a maximum height. The table then scrolls inside its own box, so both scrollbars are permanently on screen and the header stays put. This is what Sheets, Excel, Airtable, AG Grid, Metabase and GitHub Projects all do.

Note what this costs: the page scrolls, and so does the box inside it. Your wheel does one or the other depending on where the pointer is.

  • For: the most familiar answer of all — it is how every spreadsheet works. The scrollbar is on screen by construction, with no sticky trickery.
  • For: the header never leaves.
  • Against: nested scrolling. Two scroll contexts on one page is the single most complained-about pattern in data UIs, and the wheel becomes position-dependent.
  • Against: it needs a height, and no height is right for both a 2-row and a 42-row table. /transfers has one row.
  • Against: the app already paginates. Vertical scrolling inside a box that holds one page of rows is solving a problem we solved differently.
  • Against: it is a change to how every index page feels, for a horizontal problem.

  • For: about fifteen lines of code, and it puts the control where the eye already is.
  • Against: it depends on the platform drawing a native scrollbar, which is the thing that is broken. It fails exactly where it is needed.
  • Against: a scrollbar above the content it scrolls is unusual enough that people miss it.
  • Against: it duplicates the scrollbar rather than replacing it, so on platforms where both show there are two.

  • For: unmistakable, above the fold, and two ordinary buttons — nothing new for a screen reader or the keyboard.
  • For: renders identically everywhere, since it is not a scrollbar at all.
  • Against: paddles are standard for tab strips and carousels, not for data tables. I could not point at a data grid in wide use that ships them, and inventing a control is worse than adopting one.
  • Against: no position feedback. A scrollbar shows how much is left; two arrows do not.
  • Against: clicking repeatedly to cross 486px is worse than one drag.

Recommendation

The correction, plus option B.

The correction is not optional in any case: a fade over a frozen column is simply a bug, on six of the seven tables that scroll.

Then B, because it is the only one of the four that answers all three of your points. The fade told you there was more and gave you nothing to act on; B is an actual control, at the bottom of the window rather than the bottom of the table, drawn by us so that “I don't see it” cannot be a platform setting. It is also the option with real precedent for a table in page flow — Ant Design, Confluence, Jira — whereas C is precedent for a table that replaces the page.

Keep the fade. It answers a different question: the rail says you can move, the fade says there is something there. Every grid that has one has both.

And fix the suppression regardless. Dropping scrollbar-width lets the ::-webkit-scrollbar rules apply on Chrome and Safari, which is strictly better than what is shipped — but I cannot verify it here, so it stays a bonus and B stays the answer.

Not an alternative: cutting columns (distributions-columns.html). Worth doing, and measured there: it never makes the table fit on its own.
