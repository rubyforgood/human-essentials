Three causes, and only one of them is this page's fault.

  • select2 was never restyled. The chevron pass (f9f61d837) fixed its arrow and text padding but not its box, so it still carries the vendored 2014 metrics: 28px tall, 4px radius, 16px text. Six selects across five views have this, not just donations — organizations (two), product drives, served areas and partner children.
  • The row overrides the select wrapper. The partial passes wrapper: :essentials explicitly, which is the text input wrapper, so the select never reaches :essentials_select that wrapper_mappings would have given it.
  • The scanner button and the barcode input are hand-rolled class strings, not the design system's control, so nothing keeps them in step with it.

Q1 — How many columns?

The two cards above this one are both grid gap-x-5 sm:grid-cols-2 lg:grid-cols-3. The items card is a flex-wrap row with no column structure at all, which is why its controls come out 184px, 575px and 128px wide.

A caution about reading “match the convention” too literally.

The other two cards hold one form filled in once. This card holds a repeating collection, and those are different objects with different conventions. Forcing three equal columns onto a repeating row would put Item and Quantity in equal-width cells, which no inventory app does — quantity is always the narrow one. What this card should inherit is column discipline: fixed, aligned, predictable columns. That is what options B and C below give it, and what a table has always given it.

Q2 — The barcode affordance

1. Icon button beside the field today, sized correctly

Smallest change. Two boxes still read as two controls doing unrelated jobs.

2. Joined input group industry default

One control, one rectangle. Shopify, Square, Zoho and Bootstrap’s input-group all draw a scan field this way.

3. Icon inside the field

Tidiest, but a 36px hit area inside a text field is easy to miss and easy to mis-tap on touch.

4. Labelled button

Unambiguous, no aria-label needed. Costs ~40px of row width per line.

Recommendation: option 2, and move it out of the row (see Q4/C).

The icon itself is fine — bi-upc-scan is the barcode glyph Shopify, Square and Zoho all use, and swapping it for a camera would say “photo” rather than “scan”. What is wrong is its box: 42px next to a 38px field, unpadded to a 34×42 rectangle rather than a square. Joining it to the input fixes the alignment by construction, because they share one border.

The larger point is that no inventory app puts a scan field on every line. Square, Zoho Inventory, Odoo and Amazon Seller all put one scan field at the top of the receiving document; scanning appends a row. Today this page renders “Scan a barcode”, an “or”, and a full item picker per row, so a ten-line donation has ten scan fields and ten “or”s. That is the real cost, and it is what option C removes.

Q3 — The remove control

1. Text, ghost today

Remove

83px of every row. Reads as grey, though the code asks for rose-700 — the ghost variant’s own text-slate-600 collides with it and wins.

2. Icon only industry default

38px, aligned to the control line. QuickBooks, Xero, Shopify and Stripe all end a line item this way.

3. Icon + text

Clearest of the four, widest of the four.

4. Reveal on hover not recommended

There is no hover on touch, and a control that appears on approach fails WCAG 2.1 content-on-hover expectations.

Recommendation: option 2, icon-only, always visible, at the end of the row.

It is the dominant pattern for line items and it buys back ~45px of row width for the item name, which is the field that actually needs it. It needs an aria-label naming the row — design.md already requires that of icon-only controls — and it stays slate until hover, going rose only on hover and focus, so a form with eight rows does not have eight red marks down its right edge. That is the same argument that took the inline error message grey in a5cef7c35.

Whichever is chosen, the colour bug is worth fixing: passing extra: "text-rose-700" to a ghost button cannot work, because both utilities land in the class attribute and the cascade, not the attribute order, picks the winner.

Q4 — A better shape for the row

Three options, cheapest first. All three assume the select2 box fix, without which none of them line up.

Recommendation

Fix select2's box first, on its own. It is six selects, it is the single biggest visual mismatch on the page, and every option below depends on it. This is worth doing even if none of A/B/C is chosen.

Then option C, arrived at through B — B is C without the scan bar, so building B first is not wasted work if C turns out to be too much. C is the shape every inventory app converges on because it matches how receiving actually happens: you scan repeatedly into one field, and you read a list of what you have so far.

If the appetite is small, option A alone is a real improvement and touches no JavaScript: the row stops being ragged, and the scanner and remove controls stop being two sizes nothing else on the page uses.

One caveat on B and C worth stating before anything is built: the row markup is shared by seven forms — donation, purchase, distribution, transfer, adjustment, audit and kit — and the distribution form adds a “Requested” column the others do not have. Whatever is chosen has to work for all seven, or the partial has to take a variant.
