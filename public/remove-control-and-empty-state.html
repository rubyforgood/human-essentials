The remove control, and the empty state

Two questions. Hover or focus the trash icon in option B to see the tooltip behave.

1. Tooltip, or a labelled ghost button?

The app already disagrees with itself.

remove_element_button has five call sites. Four render the labelled ghost button — served areas, attached documents, and both partner request forms. Only the bank line item row is icon-only. And the closest analogue is not a distant screen: the partner request form is the same shape, a repeating row of item + quantity, and it renders "Remove" at 83×28 in rose-700 inside a real table. Whatever is chosen should probably apply to both.

Recommendation: C.

Consistency is the deciding argument and it is not a close call once you know the partner form exists: the same control, in the same kind of row, two screens apart, rendered two ways. C makes five call sites out of five, and deletes the icon_only: branch rather than spreading it.

Against my own earlier recommendation, which was the icon. That argument was about density — QuickBooks, Xero and Stripe do use bare glyphs — and it is a good argument in isolation. It is the wrong one here, because the cost of being inconsistent inside one app is larger than the 45px, and because a tooltip (B) is a whole component with WCAG 1.4.13 obligations bought to solve a problem that a word solves for free.

If density does win later, B is the honest version of A and A should not stay as it is: an icon with no hover affordance is the one option here with a real gap in it.

2. The empty state, which does not exist

Remove the last row today and the card keeps its furniture.

Measured: column headings still rendered, a 20px empty strip where the rows were, and a footer whose total is blank. design.md is explicit — "Never render bare empty table chrome" — and this card was built without one.

Always keep one blank row; the remove control on a lone row is disabled. What QuickBooks, Xero and Stripe do — there is always a line to type into. No empty state needed, but a disabled control needs explaining.

Recommendation: B, and C is a real alternative.

B uses the component the rest of the app already uses, hides the headings because there are no columns to head, and offers the action — which is what :cold_start is for. It is also the only option that says why the card is empty.

C is what the line-item editors actually do, and it is tempting: an empty state you can never reach is dead code. But it needs a disabled control on the last row, and a disabled control with no explanation is its own accessibility problem — aria-disabled plus a reason, or the user just finds a button that does nothing. B is less machinery.

Either way the footer total should disappear when there is nothing to total, rather than rendering an empty paragraph as it does now.
